> 작성: 2026-10-21
> 상태: **준비 완료 · 일부 결정 확정** (조사·스키마·복사 도구까지. 새 저장소 업로드·클라우드 리소스는 아직 만들지 않았다)

> 진행(2026-10-21): 이관 완료 — 새 저장소·새 Worker(https://smart-forms.jogh.workers.dev)·새 Supabase, 데이터 대조 일치. §3-C 중 **코드 정리를 했다**(브랜치 `chore/remove-smart-forms`: 홈 카드·라우트·API·화면·셸·서명·시험 46개·fixtures 제거). 홈의 새 주소 연결은 사용자가 따로 만들었고 리다이렉트는 두지 않는다. DB `form_*`·버킷 `form-files` 는 2026-11-04 까지 보존한다(삭제는 별도 승인). 위 "상태" 줄과 본문은 작성 당시 기록이다.
> 선례: [`2026-07-02-단열재나누기도-이관계획.md`](./2026-07-02-단열재나누기도-이관계획.md) (SSX → IPG 이관)

이 저장소(IPG, 단열 Layout 런처)의 도구 **스마트폼**(`/tools/forms`)을 **동작 그대로** 별도 저장소로 떼어낸다.

이관이 끝나 안정될 때까지 IPG 쪽 코드와 테이블은 **지우지 않는다**(되돌릴 길을 남긴다).

## 5. 사용자 식별과 로그인

- 테이블에 남는 사용자 키는 DCR 로그인 응답의 `user.id`(text)다. `uploaded_by`, `reviewed_by`, `created_by`, `updated_by`, `replaced_by`, `author_id`에 쓰인다.
- **새 앱도 같은 DCR prod(`dcr-app`)로 로그인하면** 기존 행의 `user.id`가 그대로 맞는다. 그래서 "올린 사람만 삭제" 같은 권한도 그대로 유지된다.
  - 다만 DCR dev를 가리키면 id가 다를 수 있다. 이 부분은 **미확인**이다.
- 이메일로 맞추는 곳이 3군데 있다: `form_admins` PK, 의견 글쓴이 판정, 관리자 자기삭제 방지. DCR 이메일이 바뀌면 이 셋이 깨진다. 이관 전과 같은 조건이다.
- 쿠키 `ipg_session`은 `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=12h`이고 `Domain` 속성이 없어 발급한 호스트에만 붙는다(`auth.ts:109-110`). 그래서 새 주소에서는 **모든 사용자가 한 번 다시 로그인한다**. 세션 시크릿을 공유하지 않으므로 의도된 결과다.

## 6. 데이터 이전 절차

도구는 [`scripts/smart-forms-split/copy-data.mjs`](../scripts/smart-forms-split/copy-data.mjs)다.

- 기본 실행은 dry-run이다(읽기만 한다).
- `--execute`를 주면 복사하고, 끝나면 자동으로 대조한다. `--verify`는 대조만 한다.
- PK 기준 upsert라 다시 실행해도 행이 늘지 않는다.
- 대상 URL이 원천과 같거나 IPG·SSX ref이면 실행을 거부한다.

```bash
# 시크릿은 셸 환경변수로만 넘긴다(파일·커밋 금지)
export SRC_SUPABASE_URL=https://yzercziwazfrjsjnmbhr.supabase.co
export SRC_SERVICE_ROLE_KEY=...    # IPG
export DST_SUPABASE_URL=https://<new-ref>.supabase.co
export DST_SERVICE_ROLE_KEY=...    # 새 프로젝트
node scripts/smart-forms-split/copy-data.mjs            # 1) dry-run: 원천 수량·대상 빈 상태 확인
node scripts/smart-forms-split/copy-data.mjs --execute  # 2) 복사 + 자동 대조
node scripts/smart-forms-split/copy-data.mjs --verify   # 3) 재대조(컷오버 직전)
```

| 단계 | 할 일 | 통과 기준 |
| --- | --- | --- |
| 0. 사전 | 새 Supabase에 스키마를 적용하고 새 Worker를 배포한다. 새 주소에서 빈 DB로 로그인·업로드·다운로드를 시험한다 | 시험 서류 1건이 올라가고 열린다. 시험 행은 지운다 |
| 1. 리허설 | 동결 없이 `--execute`를 한 번 실행한다(복사 시간 측정, 약 100MB) | 대조 결과가 모두 일치한다 |
| 2. 공지 | 사용자 2명 이상에게 알린다. ① 동결 시각 ② **결재 서명 재등록** ③ 화면의 동기화 배너가 "모두 올라감"인지 확인 | — |
| 3. 동결 | IPG 스마트폼에 쓰기를 막는다(방법은 결정 D4) | `form_documents` `max(updated_at)`이 더 이상 바뀌지 않는다 |
| 4. 본 복사 | `--execute` → `--verify` | 테이블 6개 행 수와 파일 164개(또는 그 시점 수)가 일치한다 |
| 5. 컷오버 | IPG 홈 카드·`/tools/forms`를 새 주소로 돌린다 | 사용자가 새 주소에서 기존 서류를 연다 |
| 6. 관찰 | 2주 동안 IPG 쪽 데이터·코드를 보존한다(읽기 전용) | 새 쪽에서 오류 의견이 처리된다 |
| 7. 정리 | §3-C를 별도 PR과 승인으로 진행한다 | — |

**되돌리기**: 5단계 이후에 문제가 생기면 홈 카드와 라우트를 원래대로 돌리고 IPG 동결을 푼다.
이때 새 쪽에서 쓴 내용은 IPG로 역복사해야 한다. 스크립트는 기본적으로 IPG를 대상으로 받지 않는다. SRC·DST를 바꾸고 `--allow-ipg-target --execute`를 함께 줄 때만 허용한다(SSX ref는 어떤 경우에도 거부).
역복사는 upsert라 새 쪽에서 **지운** 행은 IPG에 남는다. 이 경로는 가짜 서버 시험만 했고, 실제 프로젝트로는 시험하지 않았다.

| localStorage | `ipg-forms:signature:{userId}` | **결재 서명이다. 서버에 없으므로 사용자가 다시 등록해야 한다** |

서버에 한 번도 올라가지 않은 로컬 전용 서류가 있는지는 확정하지 못했다. 조사에서 `formSync`/`formMigrate`를 끝까지 읽지 않았다. 동결 전 공지의 ③항이 이 위험을 대신 막는다.

### 이관과 별개로 확인이 필요한 기존 동작

아래 항목은 그대로 옮기되, 의도인지 확인이 필요하다. 업무 규칙이 코드에도 문서에도 없어서 추측으로 정하지 않았다.

- `PATCH /docs/:id`가 `review_status`(본사 점검 ok/fix)를 바꿀 때 본사 관리자 검사가 없다(`forms.ts:759` 부근). 로그인한 누구나 점검 결과를 적을 수 있다.
- `DELETE /docs/:id`는 올린 사람 또는 role이 관리자인 사람만 허용한다. `form_admins` 명단은 인정하지 않는다(`forms.ts:831` 부근).
- `PUT/DELETE /taxonomy`가 로그인만 확인한다(`forms.ts:468-469` 주석, 2026-10-13 이후). 원 마이그레이션 머리 주석("본사 관리자만 바꾼다")과 다르다.
- `form_documents.site_id`는 `on delete cascade`다. 현장 삭제 API는 지금 없다.
